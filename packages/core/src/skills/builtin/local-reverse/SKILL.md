# Local reverse engineering

Follow the session's response language; keep tool names, addresses, hashes and evidence paths literal. Use only tools actually exposed to this agent. Read-only members must return configuration or patch needs to their coordinator rather than inventing shell or write access.

## Local analysis sequence

1. Confirm the supplied file, requested question and permitted scope. Start with `binary_triage` for format, hash, entropy and interesting strings. Strings are candidates, not proof of imports, packing or malicious behavior. Keep the sample unchanged and do not run it.
2. Use `drill_preflight` or `/drill setup` to discover this computer's tools. Discovery is not proof that a tool supports this sample or that its JDK is compatible. Use PATH or user-configured paths; never assume the developer's directories exist. `/drill tools <name> <absolute-path>` saves a local executable selection, and environment overrides take precedence. For Ghidra set `GEMINI_ULTRA_GHIDRA_HOME` to its installation root and select a compatible native Java via `GEMINI_ULTRA_TOOL_JAVA`, `JAVA_HOME`, a saved Java path, or PATH, in that order. Commercial IDA requires the user's licensed installation; Android may use installed JADX. Report a concrete missing prerequisite instead of claiming analysis succeeded.
3. Use `binary_inspect` with `view=info|imports|sections|libraries|symbols` for actual rabin2 metadata. `maxItems` bounds the list; check `truncated`, `returnedItems` and `totalItems`. Configure `GEMINI_ULTRA_TOOL_RABIN2` when needed. Its fixed read-only invocation has a 20-second timeout and does not execute the sample.
4. Use `binary_analyze` with `view=functions`, then relevant `view=instructions` and `view=xrefs` to trace callers and callees with native r2. `xrefs` requires an address. Pass the exact virtual address returned by inspection: safe integers may stay numbers; high 64-bit values must remain decimal strings or `0x` hexadecimal strings. Never convert a high address through JavaScript Number, a floating-point value or scientific notation. No r2 expressions are accepted. Instructions are a bounded window, not a complete function; empty references do not prove no callers exist. This tool ignores user startup scripts/plugins and is bounded to 30 seconds, 4 MiB output and a 64 MiB sample. Configure `GEMINI_ULTRA_TOOL_R2` when needed.
5. Use `binary_decompile` for one selected function when Ghidra and native Java are ready. Parameters are `filePath`, optional hexadecimal virtual `address`, and optional `maxChars` (1000–60000). Its address is always hexadecimal: do not pass a decimal address string unchanged. Obtain the corresponding exact hex address from evidence or convert with integer arithmetic such as `"0x" + BigInt(decimalText).toString(16)`; if this agent cannot perform a reliable conversion, ask the coordinator to supply it. Do not use a file offset as a virtual address. Omitting `address` selects an entrypoint/first function, not the function named in your question. Check the returned `functionName`, `address`, `imageBase` and `selection`; PIE/shared-library rebasing can differ from r2. Never silently substitute another function when the requested address is absent.
6. Read the full `codeArtifact` and relevant `reportArtifact`/`logArtifact` when `truncated` or when the question depends on omitted pseudocode. Preserve `sampleSha256`, `codeSha256`, `ghidraVersion` and the selected address in the handoff. If `sourceChangedDuringAnalysis` is true, distinguish the copied analyzed sample from the current source file. The tool retains full artifacts, copies rather than executes the sample, and is bounded to 120 seconds, a 1 GiB heap and a 64 MiB sample. Pseudocode is recovered analyzer output, not original source or runtime verification. For multiple functions, analyze only those needed for the requested data flow and link observations by concrete call/address evidence.

`binary_analyze` also returns `addressFormats`: each `itemIndex` identifies a returned `data` row and its `hex` object gives exact hexadecimal forms of the row's native address fields. Copy these forms when writing a call chain or passing a Ghidra address; do not recompute them mentally. For a reference, `from` is the CALL/reference instruction address while `fcn_addr` is the containing function's entry. For an instruction, `addr` (or `offset`) locates it and `jump` is its branch/call target. The original `data` remains native evidence; the formatting table covers only returned top-level fields, not omitted rows or every nested reference. If a needed field has no formatted value, retain its exact original representation and the unresolved conversion.

## Interprocedural evidence

- Build each call edge from a specific instruction/reference row: evidence file, row address, literal opcode, exact callee address. Use `addressFormats` when available; preserve exact original integers otherwise. The containing function entry (`fcn_addr`) is not the CALL instruction (`from`). Keep observations and derived conclusions separate; do not silently replace an uncertain address with a guessed conversion.
- Recover argument and return flow from the selected architecture, calling convention, register widths and concrete caller/callee instructions. On x86-64, writing `edi` or `eax` zero-extends `rdi` or `rax`; upper bits do not retain an earlier value. `ret` does not need an explicit read of `eax` to pass its value back to a caller. Absence of another local read does not establish that a return value is discarded. Trace the relevant caller or retain the uncertainty. These rules do not establish an ABI for other architectures or original source-level types.
- A recovered `(void)` prototype is not proof of no machine-level arguments. `binary_decompile.signature` is the Ghidra program-database prototype; `decompiledSignature` is the signature inferred for the pseudocode. They can differ in parameters and return type. Quote the exact field and its value separately; never attribute the C declaration to the database field. `signatureProvenance` labels each source; older reports may omit the decompiler field, which must remain unknown rather than copied from `signature`. Ghidra's compiler selection is analyzer metadata, not proof of the original compiler or language. Cross-check pseudocode against actual instructions without rewriting the analyzer output to match your hypothesis. Instruction windows, function metadata and matching counts alone do not prove all control-flow paths are covered.
- For each significant claim, provide the supporting artifact/address and a literal excerpt, the separate inference, and its unresolved limits. A computed constant is a static inference until observed at runtime; it is not a process exit code, printed value or verified vulnerability. An auditor must check the cited row and the reasoning, since an exact quotation alone does not prove the conclusion attached to it.
- Distinguish the caller's input constant, intermediate register values and the final caller-visible return value. For structured output, establish which quantity each requested field denotes, then check that JSON values and prose refer to that same quantity and width. An input constant is not a computed return value. If the requested field's meaning is ambiguous, surface that uncertainty instead of silently choosing one interpretation. Auditors must check these semantic links as well as literal quotes and arithmetic.

## Facts and collaboration

- Record relevant evidence with `drill_record_fact`, including the sample hash, artifact paths, addresses and the observed reasoning. A `vuln` fact defaults to `unverified`; use `static-reviewed` only with concrete static evidence, and `verified` only with explicitly corroborating validation described in `evidence`. Recording a fact does not verify it. Use `note` for ordinary observations. Do not promote static pseudocode or a tool's successful exit to runtime proof.
- In an existing Swarm, use the assigned public brief and `post_swarm_message`; `@name`/`@all` wakes peers. Return the full artifact paths, exact addresses, outcome and unresolved gaps through `complete_task`. Long member outputs have verified full-result archives; read them when a preview omits needed evidence. Do not repeatedly wake a completed peer. The coordinator adds or mentions an independent `workflow-auditor` after analysis is ready; a paused member or a static candidate is not a verified deliverable.
- Outside Swarm, independent tasks may use `spawn_subagents` only when that tool is exposed, with self-contained prompts and separate responsibilities. Use `redteam-analyst` with an explicitly scoped local brief and drill authorization; the role remains read-only. Direct, batch and Swarm entry points all check this existing prerequisite, including after waiting for a dispatch slot. A rejected invocation needs explicit authorization restoration and retry. Bypass mode, credentials and local authorization do not expand an external target's scope.
- Prefer read-only inspection. Any requested patch uses `verified_patch_transaction` only when available and authorized, preserving its backup and rollback artifacts for the specified target. Do not automatically launch unknown binaries or dynamic analysis. Honor the user's minimal validation requirements; do not add broad or smoke suites. Report completed observations separately from missing evidence, and preserve partial work when cancelled or blocked.

On a fresh computer run `/drill setup`, configure only the needed tools, then rerun readiness. If shell tools are needed and exposed, use the executable path returned by discovery: environment overrides do not add commands to PATH. Quote paths for the active shell; PowerShell uses `&` before a quoted executable path. If tools or formats are unavailable, return the retained artifacts and precise next prerequisite.
